The DecTog worker answers every host in the zone: the apex (`dectog.com`), the dashboard host (`app.dectog.com`, `APP_HOST`) and every account host (`<username>.dectog.com`). This page lists what each host and path does. Self-hosted deployments substitute their own `ROOT_DOMAIN`, `APP_HOST`, `WEB_URL` and `PUBLIC_BASE_URL`; see [Configuration reference](/self-hosting/configuration-reference/).

## Association files

Universal Links and App Links need two files on the account host. The worker generates both from the apps registered in [Dashboard: Apps](/dashboard/apps/); nothing is uploaded. Setup on the app side is in [Platform setup](/sdk/platform-setup/).

| Path | Built from |
|---|---|
| `/.well-known/apple-app-site-association` | Every app of the account that has both `ios_team_id` and `ios_bundle_id`. |
| `/.well-known/assetlinks.json` | Every app of the account that has `android_package`. Fingerprints come from `android_sha256_fingerprints` and default to `[]`, which never verifies. |

### Which account the file is for

1. A `?u=<username>` query parameter always wins. This is how the dashboard's Verify buttons fetch the file on the app host, and the only form that works in path mode or on `localhost`.
2. Otherwise, when `ROOT_DOMAIN` does not start with `localhost`, the first label of the Host header: `acme.dectog.com` serves the account `acme`.
3. Otherwise: `400 {"error": {"code": "invalid_request", "message": "Subdomain not found in host"}}`.

An unknown username, or a known one with no qualifying app, answers `404 {"error": {"code": "not_found", "message": "Configuration not found"}}`.

### Response

Both files are served with `content-type: application/json; charset=utf-8` and two extra headers: `x-hostname`, the request's Host header, and `x-subdomain`, the resolved username (or the first host label when none was resolved).

```json title="https://acme.dectog.com/.well-known/apple-app-site-association"
{
  "applinks": {
    "apps": [],
    "details": [
      { "appIDs": ["8H7C9JL2K3.com.example.app"], "components": [{ "/": "/*" }] }
    ]
  },
  "webcredentials": { "apps": ["8H7C9JL2K3.com.example.app"] }
}
```

One `details` entry per qualifying app; `webcredentials.apps` lists the same app ids, so password AutoFill can be associated too. Every path on the host is claimed (`/*`).

```json title="https://acme.dectog.com/.well-known/assetlinks.json"
[
  {
    "relation": ["delegate_permission/common.handle_all_urls"],
    "target": {
      "namespace": "android_app",
      "package_name": "com.example.app",
      "sha256_cert_fingerprints": ["AA:BB:CC:…"]
    }
  }
]
```

One statement per qualifying app. Include the Play App Signing certificate's fingerprint, not only your upload key's, or verification fails on devices that installed from Play.

```bash title="Check what a host serves"
curl -si https://acme.dectog.com/.well-known/apple-app-site-association
curl -s 'https://app.dectog.com/.well-known/assetlinks.json?u=acme'
```

## robots.txt and sitemap.xml

Both are generated by the worker on every host because the blog lives in the database, not in the static export.

`GET /robots.txt` (`text/plain`):

```text
User-agent: *
Allow: /
Disallow: /dashboard
Disallow: /api

Sitemap: https://app.dectog.com/sitemap.xml
```

`GET /sitemap.xml` (`application/xml`) lists `WEB_URL` plus `/`, `/about`, `/blog` and `/contact`, then `/blog/<slug>` for every published post, newest first, with `<lastmod>` set to the post's `updated_at` date (`YYYY-MM-DD`). Drafts are never listed. The origin is `WEB_URL` (`https://app.dectog.com` on the hosted service) because the apex only redirects.

## Blog post pages

The static export has no page per post. `/blog/<slug>` on the dashboard host is answered with the export's article page, `/blog/article`, which loads the post in the browser; `/blog/` is the blog itself. The article page's head has no title, description or share tags of its own. Link unfurlers never run the page's script, so for a published post the worker adds them to the head before sending the page:

| Tag | Value |
|---|---|
| `<title>` | `<post title> — DecTog Blog` |
| `description`, `og:description`, `twitter:description` | The post's excerpt. Left out when the excerpt is empty. |
| `og:title`, `twitter:title` | The post's title. |
| `og:url` | `WEB_URL` plus `/blog/<slug>`, the address the sitemap lists. |
| `og:site_name`, `og:type` | `DecTog`, `article` |
| `og:image`, `twitter:image` | The post's featured image, else the site card `WEB_URL/media/og-card.png` with its `og:image:width` (1200), `og:image:height` (630) and `og:image:alt`. |
| `twitter:card` | `summary_large_image` |

Each added tag carries a `data-post-head` attribute; the page removes them when the visitor moves on to another page of the app. The page is sent without the export's `ETag`.

Drafts, unknown slugs and HEAD requests get the article page unchanged. Once the post fails to load, the page shows "Article Not Found" and titles itself `Article Not Found — DecTog Blog`.

## Host and path routing

Some paths belong to the worker on every host: anything under `/api/`, `/r/`, `/.well-known/` and `/_/`, plus exactly `/healthz`, `/robots.txt` and `/sitemap.xml`. Everything else depends on the host. The port is ignored when matching hosts.

| Host | Path | Result |
|---|---|---|
| any | `/api/…` | The REST and admin APIs. |
| any | `/r/<username>/<slug>` | The redirect engine (path-mode link URL). |
| any except `APP_HOST` | `/?user=<username>/<slug>` | The redirect engine (query-mode link URL). |
| any | `/.well-known/…` | The association files above. |
| any | `/_/collect` | The interstitial beacon (POST). |
| any | `/healthz`, `/robots.txt`, `/sitemap.xml` | See this page. |
| `app.dectog.com` | any other path | The dashboard's static export. `/blog/<slug>` serves the export's article page, which reads the slug client-side; for a published post the worker adds the post's head tags first (see [Blog post pages](#blog-post-pages)). `/login` and `/login/` with a valid session cookie answer `302 /dashboard` with `cache-control: private, no-store`. |
| `dectog.com` | `/` | `302` to `WEB_URL`. |
| `dectog.com` | `/SKILL.md`, `/llms.txt` | Served from the dashboard's static assets, so `curl https://dectog.com/SKILL.md` works without a redirect. Without an assets binding (local development) these redirect like any other path. |
| `dectog.com` | any other path | `301` to `WEB_URL` plus the path and the query string: `https://dectog.com/contact?ref=x` goes to `https://app.dectog.com/contact?ref=x`. |
| `<username>.dectog.com` | `/` | Known username: `302` to `WEB_URL`. Unknown username: `302` to `UNKNOWN_HOST_REDIRECT` (`https://dectog.com/` on the hosted service), or `404 {"error": {"code": "not_found", "message": "Not found"}}` when it is unset. `www` is a reserved username, so `www.dectog.com` follows the unknown-host rule. |
| `<username>.dectog.com` | `/<slug>` | The redirect engine. An unknown username here also follows `UNKNOWN_HOST_REDIRECT`; an unknown slug gets the 404 page and an expired temporary link the 410 page. See [How a tap is routed](/links/how-a-tap-is-routed/). |
| `<username>.dectog.com` | two or more path segments | `404 {"error": {"code": "not_found", "message": "Not found"}}`. |

In the hosted deployment `WEB_URL` and `PUBLIC_BASE_URL` are both `https://app.dectog.com`, so the apex and account roots send visitors to the dashboard host.

### HEAD requests

There is no separate HEAD logic. A HEAD request runs the same handler as GET and the response is returned without a body, with the same status and headers. That includes the redirect engine: a HEAD to a link URL is processed like a tap. Point uptime checks at `/healthz`, not at link URLs.

## Health check

`GET /healthz` answers on every host:

```json
{ "ok": true, "service": "dectog", "version": "v1", "host": "app.dectog.com" }
```

`host` echoes the request's Host header (`null` when absent). The route needs no authentication and is not rate limited.
