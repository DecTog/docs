Production is the `production` environment in `apps/worker/wrangler.jsonc`: one Worker bound to two routes on your zone, one D1 database, two cron triggers and a static-assets binding that serves the dashboard. The same Worker answers the API, the admin API, the link redirects, the well-known files and the dashboard host.

## Cloudflare prerequisites

- A zone on Cloudflare (the reference configuration uses `dectog.com`). Replace it with your own domain everywhere below.
- DNS, both proxied (orange cloud): a record for the apex, and a wildcard record `*` pointing at the apex. Worker routes only see traffic that passes through Cloudflare's proxy, so an unproxied record never reaches the Worker. Tenant links live on `<username>.<ROOT_DOMAIN>` and the dashboard on `APP_HOST` (`app.<ROOT_DOMAIN>`), and the wildcard covers both.
- Two routes with `zone_name` set: `<root>/*` and `*.<root>/*`. A more specific route in the same zone (for example a separate docs site on `docs.<root>/*`) takes precedence over the wildcard without any change here.
- Usernames `app`, `www`, `api`, `links`, `dashboard`, `admin`, `mail`, `static` and `cdn` are reserved (`apps/worker/src/bootstrap.ts`), so no tenant can claim those hosts. Any other subdomain you use for something else can be claimed by a signup unless you add it to that list or close signups with `OPEN_SIGNUPS="0"`.
- Node 22.12 or newer and a `wrangler login` session on the account that owns the zone (`npx wrangler whoami`).

## The production environment

Edit `env.production` in `apps/worker/wrangler.jsonc`. The file as shipped carries the hosted service's domain and D1 id; replace every value marked here.

```jsonc title="apps/worker/wrangler.jsonc (env.production)"
"production": {
  "routes": [
    { "pattern": "example.com/*", "zone_name": "example.com" },
    { "pattern": "*.example.com/*", "zone_name": "example.com" }
  ],
  "vars": {
    "ENVIRONMENT": "production",
    "ROOT_DOMAIN": "example.com",
    "LINK_URL_MODE": "subdomain",
    "PUBLIC_BASE_URL": "https://app.example.com",
    "WEB_URL": "https://app.example.com",
    "APP_HOST": "app.example.com",
    "UNKNOWN_HOST_REDIRECT": "https://example.com/",
    "RETENTION_DAYS": "400",
    "ATTRIBUTION_WINDOW_HOURS": "24"
  },
  "triggers": { "crons": ["17 3 * * *", "7 * * * *"] },
  "d1_databases": [
    { "binding": "DB", "database_name": "dectog", "database_id": "<id printed by wrangler d1 create>", "migrations_dir": "migrations" }
  ],
  "assets": { "directory": "../web/out", "binding": "ASSETS", "run_worker_first": true, "html_handling": "auto-trailing-slash" }
}
```

`run_worker_first` matters: the Worker decides every request before the asset server does, so `<tenant>.<root>/login` is a link slug, not the dashboard's login page. Every variable is described on the [Configuration reference](/self-hosting/configuration-reference/). Add `"OPEN_SIGNUPS": "0"` to `vars` if only you should have an account, and `"EMAIL_FROM"` with a sender you verified in Resend if you set `RESEND_API_KEY`.

## First-time setup

<Steps>

1. Create the database and copy its id into `env.production.d1_databases[0].database_id`.

   ```bash
   cd apps/worker
   npx wrangler whoami
   npx wrangler d1 create dectog          # add --location <weur|eeur|apac|oc|wnam|enam> to pin a region
   ```

2. Set the secrets. `JWT_SECRET` and `IP_SALT` are mandatory; `BOOTSTRAP_TOKEN` is needed once.

   ```bash
   npx wrangler secret put JWT_SECRET --env production       # openssl rand -hex 32
   npx wrangler secret put IP_SALT --env production          # openssl rand -hex 32
   npx wrangler secret put BOOTSTRAP_TOKEN --env production  # any random string; deleted after step 6
   # optional
   npx wrangler secret put RESEND_API_KEY --env production
   npx wrangler secret put GOOGLE_CLIENT_ID --env production
   npx wrangler secret put GOOGLE_CLIENT_SECRET --env production
   ```

   Without `IP_SALT` a production Worker throws (`IP_SALT is not set`, naming the `wrangler secret put` command) on the first request that hashes an IP: every link tap, install, app open and beacon. The Google redirect URI to register is `<WEB_URL>/api/auth/google/callback`.

3. Apply the migrations to the remote database.

   ```bash
   npx wrangler d1 migrations apply DB --remote --env production
   ```

4. Build the dashboard's static export. The production assets binding reads `apps/web/out`.

   ```bash
   (cd ../web && npm ci && npm run build:static)             # NEXT_OUTPUT=export next build
   ```

5. Deploy.

   ```bash
   npx wrangler deploy --env production
   ```

   Wrangler names the Worker `dectog-worker-production` and attaches the two routes, the crons and the assets.

6. Create the owner account. The body form is the only one production accepts.

   ```bash
   curl -s -X POST https://app.example.com/api/admin/bootstrap \
     -H "x-bootstrap-token: $BOOTSTRAP_TOKEN" \
     -H 'content-type: application/json' \
     -d '{"email":"you@example.com","password":"<at least 12 characters>","username":"acme"}'
   # {"ok":true,"email":"you@example.com","username":"acme","api_key":"dtg_…","demo":false}
   ```

   The key is shown here and again in Settings (it was encrypted with the `JWT_SECRET` you set in step 2). Status codes and validation messages are on the [Local quick start](/self-hosting/local-quick-start/). Then remove the token; with `ENVIRONMENT=production` and no token, every further bootstrap call is `403`.

   ```bash
   npx wrangler secret delete BOOTSTRAP_TOKEN --env production
   ```

7. Sign in at `https://app.example.com/login`, register your app under Apps (bundle id, Team ID, package, SHA-256 fingerprints, store URLs) and use the Verify buttons, which fetch `https://<username>.example.com/.well-known/apple-app-site-association` and `assetlinks.json` as a device would. See [Apps](/dashboard/apps/) and [Platform setup](/sdk/platform-setup/).

</Steps>

## Every release

Run these in order from `apps/worker`:

1. `git pull`, then `npm ci` here and in `../web`.
2. `npm test` and `npm run typecheck` (worker), `npm run typecheck` (web). Optional, recommended.
3. `npx wrangler d1 migrations apply DB --remote --env production`. Applying a migration while the old Worker is still live is safe when it only adds nullable or defaulted columns and indexes, which every migration after 0015 does; the old Worker ignores columns it does not know. The command prints which files it applied; `npx wrangler d1 migrations list DB --remote --env production` shows what is pending.
4. `(cd ../web && npm run build:static)` so the deploy ships the current dashboard. Skipping this deploys the Worker with whatever `apps/web/out` already holds.
5. `npx wrangler deploy --env production`.
6. The smoke checks below.

<Aside type="danger" title="Do not use the npm scripts for production">
`npm run deploy` runs plain `wrangler deploy`, which reads the top-level (development) configuration: `ROOT_DOMAIN=localhost:8787`, `LINK_URL_MODE=path`, `WEB_URL=http://localhost:3000`, no `ENVIRONMENT`, no routes, no assets binding and the placeholder D1 id `local-dev`. It never touches your production routes, but it creates or updates a separate `dectog-worker` Worker with that configuration. The same applies to `npm run db:migrate:remote` (`wrangler d1 migrations apply DB --remote` without `--env production`), which targets the placeholder id. Always pass `--env production` to `wrangler` directly.
</Aside>

## Smoke checks

| Command | Expected |
|---|---|
| `curl -s https://app.example.com/healthz` | `{"ok":true,"service":"dectog","version":"v1","host":"app.example.com"}` |
| `curl -s https://app.example.com/api/v1/links` | `401 {"error":{"code":"missing_api_key","message":"Missing API key",…}}` |
| `curl -sI https://app.example.com/` | `200`, `text/html` (the dashboard's static export) |
| `curl -sI https://example.com/` | `302` to `WEB_URL` |
| `curl -sI https://no-such-user.example.com/` | `302` to `UNKNOWN_HOST_REDIRECT` (or `404` when it is unset) |
| `curl -sI https://<username>.example.com/<slug>` with a desktop User-Agent | `200` QR page, or `302` to a desktop redirect or fallback URL if the link has one |
| `curl -s https://<username>.example.com/.well-known/apple-app-site-association` | The AASA JSON once an app with bundle id and Team ID exists, otherwise `404 {"error":{"code":"not_found","message":"Configuration not found"}}` |
| `npx wrangler deployments list --env production` | The new version at the top |
| Cloudflare dashboard, Worker, Settings, Triggers | Cron triggers `17 3 * * *` and `7 * * * *` |

`npx wrangler tail --env production` streams the Worker's console output, including the password-reset link when `RESEND_API_KEY` is unset and the warnings from webhook deliveries and Apple Search Ads calls.

## Rollback

```bash
npx wrangler deployments list --env production
npx wrangler rollback --env production            # or: rollback <version-id> --env production
```

D1 data persists across rollbacks. A rollback does not undo migrations, and migrations are never reverted: an older Worker then runs against a newer schema. Migrations that add nullable columns or indexes are harmless for it; a migration that rebuilds a table or adds a `NOT NULL` column without a default is not, so read the migration you are rolling back across. The list is on [Database and migrations](/self-hosting/database-and-migrations/).

## What `ENVIRONMENT=production` changes

| Behavior | Without it | With it |
|---|---|---|
| Bootstrap token | Required only when `BOOTSTRAP_TOKEN` is set | Always required; with no token configured every bootstrap call is `403 Bootstrap not permitted` |
| Demo seed (empty-body bootstrap) | Allowed on an empty database | `403 Demo seed is disabled in production` |
| `IP_SALT` missing | Falls back to `dtg-default-salt` with a console warning | Throws on every request that hashes an IP |

Nothing else reads `ENVIRONMENT`. Signup stays open unless `OPEN_SIGNUPS="0"` is set, CORS follows `WEB_URL`, and the `Secure` cookie flag follows the request scheme (`https`), not this variable. The demo-login hint on the login page disappears with the static export (`NEXT_OUTPUT=export`), not with this variable.

## Strings that stay hard-coded

A self-hosted instance keeps a few DecTog references in code: the brand name `DecTog` in page titles and the "Powered by DecTog" footer of the QR page (`apps/worker/src/brand.ts`), the `Go to DecTog` button on the 404 and 410 pages (`https://dectog.com/`), the password-reset email's `Reply-To: hello@dectog.com` and default sender (`apps/worker/src/email.ts`), the `.dectog.com` hint under the signup form, and the marketing pages of the Next.js app. Change them in the source before you build if they matter to you.
